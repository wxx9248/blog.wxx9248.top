## 0x00 はじめに

初めてC++のテンプレートを書くとき、たいていは関数テンプレート/クラステンプレートを普通の関数/クラスと同じように扱おうとします：\
テンプレートの宣言を.hppファイルに、定義を別の.cppファイルに置き、ほかのファイルはテンプレートのヘッダファイルをインクルードする。\
そして意気揚々とコンパイルしてみると、リンカが訳の分からない「undefined reference」のうめき声を大量に上げるのです……

いったいなぜでしょうか？<del>人間性のゆがみなのか、それとも道徳の崩壊なのか？</del>

この記事では、テンプレートの宣言と定義をそのまま分離するとなぜエラーになるのか、そしてよく使われる解決策を見ていきます。

## 0x01 原因の分析

### ビルドの過程

まず、コンパイラがプロジェクトをどのようにビルドするのかを押さえておく必要があります。

#### 翻訳単位

最初に、翻訳単位という概念を定義しておきます。

> In C and C++ programming language terminology, a **translation unit** is the ultimate input to a C or C++ compiler from which an object file is generated. (Wikipedia)

大意は、翻訳単位とはC/C++コンパイラに**一つの**オブジェクトファイルを生成させる最終的な入力だ、ということです。

つまり、一つのオブジェクトファイルをコンパイルするのに必要な入力の集合が、一つの翻訳単位です。\
通常、コンパイラは.cppファイルごとに一つのオブジェクトファイルを生成するので、\
一般に**一つの.cppファイルが一つの翻訳単位**だと考えます。

#### コンパイル

大規模なプロジェクトには、必ず複数の翻訳単位があります。では、コンパイラは複数の翻訳単位をどう処理するのでしょうか？

翻訳単位の定義を考えると、実際の.cppファイル一つ一つに対して、コンパイラは個別にオブジェクトファイルを生成します。\
そして一つの翻訳単位を処理している間、ほかの単位はコンパイラからは**まったく見えません**。

これが翻訳単位が「単位」と呼ばれる理由でもあります：一つの翻訳単位は一つの論理的なブロックです。\
コンパイラにとって、その中にはたくさんの関数が入っているだけです。\
コンパイラの仕事は、各関数のコードを機械語に変換し、呼び出せるように入口のラベルを残しておくことだけです。それ以上のことはしません。

では外部の関数はどうなるのか、と思う人もいるでしょう。ほかの単位が見えないなら、ほかの単位の関数が呼び出されたらどうするのか？\
コンパイラいわく：知ったことではない。知らないシンボルがある？試験で解けない問題が出たらどうする？\
印を付けておけばいい。この問題は分からないから放っておいて、自分の作業を続ける。

#### リンク

ご存じのとおり、コンパイルが終わったら次はリンクです。

リンカはオブジェクトファイルをすべてメモリに読み込み、コンパイラが生成したオブジェクトファイルを一つずつ総合的に分析して、コンパイラの尻拭いの方法を考えます。\
コンパイラが知らないシンボルを山ほど残していったので、リンカは言います：まずこれらのシンボルに番号を振っておこう、あとで探しやすいように。\
番号を振り終えたら、リンカは眺めてみます：ああ、このシンボルは知っている、あのオブジェクトファイルの中にある。jmpを書いて、CPUにそこへジャンプして実行させよう。\
ああ、このシンボルはランタイムライブラリにあるようだ。これにも番号を振って、jmpを入れてCPUにそこで実行させよう……

作業が終わると、リンカは答案をもう一度見直します。\
リンカが「おや、ここにも知らないのがいくつかある」と気づいたらどうするか？しょうがない\~バグを作った人に責任を押し付けて、undefined referenceの出番です\~\
シンボルの行き先がすべて見つかったら、プラットフォームのスタートアップコードを写して、リンク済みのオブジェクトファイルに貼り付けて出力します。

<del>そしてバグを作った人はランタイムエラーの魔の手に落ちていく……</del>

### テンプレートの特徴

テンプレートには、どんな特徴（落とし穴）があるのでしょうか？

C++の規格は、使われるテンプレートだけを、使われる型についてだけインスタンス化すると明確に定めています。\
つまり、コンパイラはテンプレートが**使われたときにだけ**、それに対応するオブジェクトコードを生成します。\
テンプレートが使われなければ、対応するオブジェクトコードの中にそのコードは見当たりません。

テンプレートという概念はコンパイル時にしか存在しません。テンプレートを使わない（テンプレートのジェネリック型に具体的な型を与えない）と、\
コンパイラは手の付けようがありません。コードを機械語にコンパイルしなければなりませんが、機械語にはジェネリクスという概念はなく、\
すべて具体的な命令の並びだからです。CPUはスタック操作やポインタ演算で具体的な値を必要とします。具体的な型がなければ、\
コンパイラはその型のサイズが分からず、演算に必要な値を計算することもできません。

### 真相

答えはもう明らかでしょう。

プロジェクトに次のファイルがあるとします：main.cpp、template.cpp、template.hpp、Makefile

template.hppにはテンプレートの宣言が、template.cppにはテンプレートの定義が入っていて、\
main.cppは関数テンプレートを直接呼び出しています。template.cppとmain.cppはどちらもtemplate.hppをインクルードしています。

コンパイラはmain.cppをコンパイルするとき、（インクルードした.hppの中に）関数の宣言だけがあって定義がないことに気づきます。\
これは外部シンボルかもしれないと考えて印を付け、オブジェクトファイルを出力し、責任をリンカに押し付けます。

コンパイラはtemplate.cppをコンパイルするとき、テンプレートの宣言と定義はあるものの、この関数テンプレートをどこでも使っていないようだと気づきます。\
そこでコンパイラはこの関数テンプレートを無視して、**空の**オブジェクトファイルを出力します。

リンカはこの二つのオブジェクトファイルを受け取って途方に暮れます：コンパイラから渡されたmain.oには外部シンボルが一つあるのに、\
ほかのどのオブジェクトファイル（およびシステムのランタイムライブラリ）にも対応するシンボルが見つからない……\
そこでリンカはあきらめて「undefined reference」と一言出力し、バグを作った本人に分析を丸投げします。

## 0x02 解決策

### 一般的な解決策

よくあるC++の入門チュートリアルや、手間を省きたい回答者は、定義もヘッダファイルに入れてしまえと言います。\
そうすればどの.cppファイルにもテンプレートが行き渡り、シンボルが見つからない問題は起きません。

しかしこうすると、ヘッダファイルがかなり大きくなります。コードを読んだり保守したりする人にとって不便なだけでなく、\
プリプロセッサやコンパイラにも大きな負担がかかり、プロジェクト全体のビルドが遅くなって、時間も計算資源も無駄になります。

さらに、この方法ではテンプレートをモジュール化できません。すべての関数テンプレートが、ばらばらの実行ファイルやDLLにコンパイルされてしまいます。\
これはプログラムのバイナリレベルでの結合度を高め、逆アセンブルやデバッグをしにくくします。

### 一歩進んだ解決策

テンプレートの定義を別の.ippファイルに置き、\
テンプレートの宣言を入れた.hppヘッダファイルの最後の行で.ippファイルをインクルードする、という方法を勧めるチュートリアルや書籍もあります。

こうするとコードの保守が楽になります。\
また、テンプレートを利用者が**自由にインスタンス化**できるようにしたいなら、これが第一の選択肢のようです。\
有名なサードパーティのC++ライブラリ<a href="https://www.boost.org">Boost</a>も\
この方法を採っています：そのテンプレートには、妥当な型なら何でも渡せます。

しかし、これではコンパイラの負担は軽くならず、バイナリレベルの結合の問題も解決しません。\
もっと良い解決策はないのでしょうか？

### おすすめの解決策

一般におすすめなのは、テンプレートの宣言と定義をtemplate.hppとtemplate.cppに分け、\
template.cppの中で、ほかの.cppファイルが必要とするすべての型についてテンプレートを**明示的にインスタンス化**しておく方法です。\
こうすれば、コンパイラはテンプレートの定義をコンパイルするときに対応するコードを生成するので、リンカがシンボルを見つけられないこともなくなります。

あるいは工夫して、明示的インスタンス化の文を別のtemp_instantiation.hppファイルに分け、template.cppでそれをインクルードしてもかまいません。\
ただし、このヘッダファイルはほかの.cppファイルからインクルード**してはいけません**。

同時に、インスタンス化されたテンプレートのオブジェクトコードは、対応する名前のオブジェクトファイルに格納されるので、\
バイナリレベルの結合の問題も解決します。\
インスタンス化されたテンプレートのコードをDLLにコンパイルして、ソフトウェアと一緒に配布することもできます。

この方法の唯一の欠点は、テンプレートを**自由にインスタンス化できない**ことです。\
プログラムのほかの場所で使う前に、テンプレートの**定義**ファイルで対応する型についてテンプレートを手作業で明示的にインスタンス化しておく必要があります。\
明示的にインスタンス化されていない型については、リンカが「undefined reference」エラーを出します。

サンプルコード：

```makefile title="Makefile"
OUT=Test.exe
OBJ= main.o template.o
CC=g++

Test: $(OBJ)
	$(CC) -s -o $(OUT) $(OBJ)

main.o: template.hpp
template.o: template.hpp

.PHONY: clean run
clean:
	rm -rf *.exe *.o

run:
	.\\$(OUT)
```

```cpp title="main.cpp"
#include <iostream>
#include "template.hpp"

int main()
{
    using namespace std;
    cout << add(1, 2.0f) << endl; // add<int, float>しか使えず、ほかの型は使えない
    return 0;
}
```

```cpp title="template.hpp"
#ifndef TEMPLATE_HPP
#define TEMPLATE_HPP

template <class T1, class T2>
auto add(const T1 &a, const T2 &b) -> decltype (a + b);

#endif
```

```cpp title="template.cpp"
#include "template.hpp"

template <class T1, class T2>
auto add(const T1 &a, const T2 &b) -> decltype (a + b)
{
    return a + b;
}

// 明示的インスタンス化
template
auto add<int, float>(const int &a, const float &b) -> decltype (a + b);
```
